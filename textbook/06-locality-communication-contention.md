## 0. 工作分得一样多，为什么仍然很慢？

想象四个人合作做一张表。每人负责四分之一的格子，工作量看起来很公平。但更新一个格子时，还要看上下左右的格子。如果相关数据都在手边，计算很快；如果每次都要停下来问旁边的人，时间就会花在等待上。

并行程序也有这个问题。上一类优化关心“谁做多少工作”，本章进一步关心“做这些工作需要的数据在哪里”。即使每个线程分到同样多的计算，也可能因为反复读内存、互相传数据或争抢共享资源而很慢。

先记住三个词的直观含义：

| 概念 | 可以怎样理解 | 程序里的例子 |
| --- | --- | --- |
| 局部性（Locality） | 需要的东西尽量在手边，用过后趁热再用 | 重复使用仍在缓存中的数据 |
| 通信（Communication） | 把数据从所在位置搬到使用位置 | 从主存读数据；向另一台机器传边界行 |
| 竞争（Contention） | 很多人同时使用同一个有限资源 | 多个线程争同一把锁或同一条内存通道 |

它们是连在一起的：数据离得远，需要搬运；搬得太多，通道会忙；很多请求同时到达，又会排队。接下来我们先看数据怎样到达处理器，再用一张网格把问题具体化。

## 1. 共享地址空间没有消除通信

### 1.1 “我能读这个数”，不等于“这个数就在手边”

共享数组让多个线程都能写出 `A[i]`。这表达的是：这些线程可以访问同一个数据。至于数据此刻在什么位置、要经过多远的路径才能取到，则由硬件和运行时决定。

CPU 周围有几层存储。**寄存器**直接供计算指令使用；**缓存（Cache）**保存一部分可能很快再次用到的数据；**主存（DRAM）**容量较大，但一般比缓存更远、访问更慢。可以把缓存理解为工作台，主存理解为仓库：工作台放不下所有材料，但常用材料放在台面上会方便很多。

当 CPU 读取一个地址时，大致会遇到这样的情况：

```text
要读 A[i]
  ├─ 附近的缓存里已经有 → 直接使用
  └─ 没有 → 去更远的缓存或主存取
                    ↓
             数据回来后才能继续使用
```

这是概念图，具体处理器的路径会更复杂。缓存里找不到所需数据，称为一次缓存未命中（Cache Miss）。硬件通常也不是只取一个数，而是搬一整条**缓存行（Cache Line）**。因此，只用到其中一个数，也可能要搬来一整行。

**作者理解：** 共享内存省掉的是程序员显式写“发送给谁”的步骤，数据移动这件事仍然存在。优化共享内存程序，同样需要关心数据的位置和搬运次数。

### 1.2 同一个地址，也可能有远近之分

有些服务器装有两个 CPU 插槽，各自连接一部分内存。假设数组主要存放在插槽 A 连接的内存中：A 上的核心读取它可以走较近的路径；B 上的核心读取它，可能还要经过插槽之间的互连。

这种访问成本随位置而不同的情况，叫 **NUMA：非均匀内存访问**。因此，数据分配在哪个内存节点、线程运行在哪里，都可能影响性能。

即便不考虑双插槽，缓存是否命中、互连是否繁忙、内存控制器前面是否排队，也都会改变一次读取的代价。课件中的环形互连和交叉开关是帮助理解路径的历史架构示例，不代表所有现代处理器采用相同结构。

### 1.3 数据放得近，还要保证用得对

多个核心缓存了同一份数据时，硬件需要协调副本，这就是**缓存一致性**处理的问题。但副本协调不能代替程序同步：两个线程同时修改同一个普通变量，仍可能产生数据竞争。

可以把三个问题分开想：

- **能不能访问？** 由地址空间和编程模型决定。
- **访问要花多久？** 与数据位置、搬运路径和排队有关。
- **并发访问是否正确？** 需要程序满足同步与内存模型的要求。

这三个问题分清后，就不容易把“共享数组很方便”误解为“共享数组没有通信成本”。

## 2. 消息传递：把隐含的数据移动写出来

### 2.1 从“读别人的数组”变成“请别人发一份”

换一种编程方式：每个参与者只管理自己的数组，不能直接读取别人的私有数组。需要邻居的数据时，就发送请求或接收对方提供的数据。这叫**消息传递**。

本章把参与者称为 **Rank**，可理解为进程编号。Rank 0 不一定就是物理核心 0；一个进程也可以在内部使用多个线程。

```text
Rank 0 的私有数组 A              Rank 1 的私有数组 B
A[3] = 7
   └── 把数值 7 发给 Rank 1 ────> 存进 B[0]
```

这里传过去的是数值，不是一个可以跨进程直接解引用的指针。发送时要说明目标和消息标记；接收时也要知道等谁、等哪类消息。消息标记通常称为 Tag，可以区分“本轮的上边界”和“另一阶段的其他数据”。

消息传递可用于多台机器，也可以在同一台机器的多个进程之间使用；运行时甚至可能用共享内存实现本机消息。所以，共享内存和消息传递首先是表达通信的方式，不应简单等同于某种硬件。

### 2.2 先看一个最容易卡住的协议

假设我们使用一个简化规则：**发送方必须等到对方接收数据，发送操作才能结束。** 这类似两个人当面交接文件，必须有人接过去，交接才算完成。

如果两边都写“先发送，再接收”，就会出现：

```text
Rank 0：等 Rank 1 来接，才能往下执行
Rank 1：等 Rank 0 来接，才能往下执行

两边都停在发送处，谁也走不到接收 → 死锁
```

死锁与“网络慢一点”不同：这里没有任何一方能推进。解决方法必须打破等待环，而不是一味等下去。

某些真实系统会先把小消息放到内部缓冲区，因此这样的代码可能偶尔跑通。但它仍可能在消息变大后卡住。不能把“这次跑完了”当作协议正确的证明。

### 2.3 让一边先收，另一边先发

只有两个 Rank 时，最直接的安排是：Rank 0 先发再收，Rank 1 先收再发。

```text
第一步：Rank 0 发送 ───> Rank 1 接收
第二步：Rank 0 接收 <─── Rank 1 发送
```

若有一条由多个 Rank 组成的链，可以按奇偶编号安排配对：

| Rank | 依次执行的操作，缺少邻居时跳过 |
| --- | --- |
| 偶数 r | 向右邻居 r+1 发送、接收；再向左邻居 r−1 发送、接收 |
| 奇数 r | 从左邻居 r−1 接收、回复；再从右邻居 r+1 接收、回复 |

例如 0、1、2、3 四个 Rank，先完成 (0,1) 和 (2,3) 的交接，再完成 (1,2) 的交接。每个配对内部都有一边发、一边收，因此可以向前推进。

这个结论依赖“链”和上表的具体顺序。改成首尾相接的环、插入额外消息后，需要重新检查等待关系。后面的 Python 程序会逐步模拟这个协议，并检测无法推进的情况。

### 2.4 非阻塞：先发起，稍后再确认完成

如果发送时只能站着等，我们就无法利用这段时间做其他事。**非阻塞通信**把“发起操作”和“确认完成”分开：先提交请求，接着做不依赖这份数据的工作，最后再等待结果。

```text
发起接收和发送
       ↓
计算不需要新消息的部分
       ↓
确认通信完成
       ↓
使用收到的数据，或复用发送缓冲区
```

代价是程序员要管理数据的使用时机。发送还没完成，不能修改或释放正在发送的缓冲区；接收还没完成，不能读取或改写接收缓冲区。类似把一份文件交给别人复印：对方尚未复制完，就改动原件，拿到的内容可能不再是你原本想发送的版本。

非阻塞提供了重叠的机会，但是否真能在后台持续传输，还取决于通信库、硬件和程序执行方式。第 4 节会讨论它怎样减少等待。

### 2.5 第二遍阅读：真实 MPI 的“完成”更精确

MPI 是常用的消息传递接口标准。前面的当面交接模型便于分析死锁，但真实接口不能都按同一种规则理解。

| 接口或模型 | 返回或完成主要保证什么？ |
| --- | --- |
| 本章的简化会合发送 | 数据已由匹配接收交付，发送才返回 |
| 标准模式的阻塞 `MPI_Send` | 发送缓冲区可以复用；消息也可能仍在系统缓冲区中 |
| 同步模式的阻塞 `MPI_Ssend` | 发送缓冲区可以复用，匹配接收已启动并开始接收 |
| 非阻塞 `MPI_Isend` | 只是发起发送，之后还需确认请求完成 |
| 非阻塞接收请求完成 | 应用可以访问收到的数据 |

所以，`MPI_Send` 返回不等于“对方已经处理完消息”。若业务需要知道处理结束，还要另发确认。`MPI_Ssend` 完成也不表示对方应用已经从接收调用返回。

MPI 的 `Sendrecv` 可以把发送和接收组合起来，常用于邻居交换；仍需正确匹配来源、目标、Tag 与缓冲区。本章没有运行真实 MPI，实验验证的是明确规定的协议模型。

## 3. 幽灵行：在本地保存远端邻居的副本

### 3.1 先明确我们究竟在更新什么

继续使用开头的网格。内部有 N×N 个点，四周还有一圈固定边界，所以实际数组大小是 (N+2)×(N+2)。内部编号从 1 到 N，边界位于 0 和 N+1。

一次更新取当前点与上下左右邻居的平均值：

$$
u_{i,j}\leftarrow\frac{u_{i,j}+u_{i-1,j}+u_{i+1,j}+u_{i,j-1}+u_{i,j+1}}{5}
$$

例如一个点当前为 10，四个邻居分别是 20、10、0、10，更新后就是 `(10+20+10+0+10)/5=10`。这个规则包含自身，共五项；它是本章的教学更新规则。

为了完整复现，我们约定初始内部全为 0，第 0 行全为 1，其余边界为 0，上方两角也随第 0 行为 1。边界始终不更新。

### 3.2 为什么分成红色和黑色两轮更新？

如果一边读数组、一边原地改数组，一个点就可能读到别人刚写入的新值。为了明确更新次序，我们把网格像棋盘一样染成两种颜色：`(i+j)%2=0` 为红，等于 1 为黑。

```text
红 黑 红 黑
黑 红 黑 红
红 黑 红 黑
黑 红 黑 红
```

一个红点的上下左右全是黑点，反之亦然。因此可以先更新所有红点，再更新所有黑点：同色点不会读取其他同色点正在改写的位置。两种颜色都更新一次，叫一个完整轮次（Sweep）。

这里真正重要的是“这次读取用哪个版本”。红阶段读取黑点的旧值；黑阶段则要读取红点刚更新的值。它与从左到右、从上到下逐点原地更新的算法不是同一种迭代顺序。

### 3.3 把网格切给两个人，边缘马上出现了问题

取 N=8，把前四行交给 Rank 0，后四行交给 Rank 1。Rank 0 更新第 4 行时，需要读第 5 行；Rank 1 更新第 5 行时，需要读第 4 行。它们都需要一部分不归自己所有的数据。

解决办法是在各自数组旁边留一行，专门存邻居边界的副本。这一行称为**幽灵行（Ghost Row）**，也属于常说的 **Halo（晕区）**。

```text
Rank 0                          Rank 1
固定上边界                     第 4 行的副本 ← Rank 0 发来
拥有第 1 行                    拥有第 5 行
拥有第 2 行                    拥有第 6 行
拥有第 3 行                    拥有第 7 行
拥有第 4 行                    拥有第 8 行
第 5 行的副本 ← Rank 1 发来     固定下边界
```

这样，更新本地边缘时，只要读本地的幽灵行即可，不必为每个点单独询问邻居。但幽灵行只是副本：本地 Rank 不负责更新它，只负责在合适的时机接收新版本。

### 3.4 交换的是数据，也是在对齐版本

一个简单而容易验证的执行顺序是：

1. 交换边界行并等待完成，准备红阶段要读的数据。
2. 各自更新拥有区域内的红点。
3. 再交换一次边界行，把刚更新的红值传给邻居。
4. 各自更新拥有区域内的黑点。
5. 下一轮开始时再交换，把新的黑值传出去。

为什么不能第一步交换一次，就连续算完两种颜色？因为第三步之前，幽灵行里的红值还是旧的。黑色边缘点会读错版本，结果就不再与我们定义的红黑算法一致。

**作者理解：** Halo 不只是“把远处的数据搬近”，还约定了“这一阶段读到哪一版数据”。先保证版本正确，再考虑怎样少发、怎样重叠，思路会清楚很多。

实验每次发送完整的 N+2 项边界行，包含两端边界列。N=8、P=2 时，一次交换两个方向各发 10 项，总共 20 项；一个完整轮次交换两次，共 40 项。只打包本阶段有用的颜色可以减少载荷，但需要额外的打包与索引工作。

### 3.5 多个 Rank 时，怎样分配行号？

下面是把两人例子推广到 P 个 Rank 的一般写法，第一次阅读只需理解“每人得到连续若干行，外加上下两行副本”。实验要求 `1≤P≤N`，确保每人至少拥有一行。

定义 ℓr 为 Rank r 前面已经分出去的内部行数，hr 为它拥有的行数：

$$
\ell_r=\left\lfloor\frac{rN}{P}\right\rfloor,\qquad h_r=\left\lfloor\frac{(r+1)N}{P}\right\rfloor-\ell_r
$$

Rank r 拥有全局第 ℓr+1 到 ℓr+hr 行。本地数组从 0 编号，拥有行在 1…hr；本地行 0 和 hr+1 放上下副本，或最外侧的固定边界。

例如 N=5、P=2，Rank 0 拥有全局行 1、2；Rank 1 拥有行 3、4、5。Rank 1 的本地行 1 对应全局行 3。判断颜色要用全局位置 `(ℓr+i+j)%2`，不能仅看本地下标，否则某些分区的红黑会反过来。

最上、最下的物理边界需要初始化；“没有邻居给我发消息”不等于可以不管这一行。如果 P>N，就需要另行定义空分块行为，本实验不覆盖这种情况。

### 3.6 判断全局结束，也需要通信

如果每人只知道自己更新了多少，怎样知道整张网格已经变化很小？一种办法是各自计算变化量的绝对值之和，再汇总起来，除以总点数 N²，由一个协调者决定是否停止，并通知其他人。

这种“把许多局部结果合成一个全局结果”的操作叫**归约（Reduction）**。通知停止或继续，则可以通过广播完成。

即使没有写出 `barrier()`，等其他人的局部结果、等继续通知，仍然包含同步。邻居交换只约束相关邻居，全局归约则涉及所有参与者；两者的等待范围不同。

本章 Halo 实验执行固定轮数，以便单独检查交换与更新是否正确，不实现完整的收敛停止协议。课件相关伪代码存在循环边界、拼写和红黑阶段省略，实验采用了补全后的明确算法，修正详情见章末来源记录。

## 4. 通信成本：延迟、带宽、重叠

### 4.1 发很多小包，为什么可能比发一个大包慢？

发送一条消息，通常既要付一次固定启动成本，也要花时间把数据传完。用 α 表示启动时间，q 表示字节数，B 表示每秒能持续传输的字节数，可以写成：

$$
T_{\mathrm{msg}}\approx\alpha+\frac{q}{B}
$$

这类似寄快递：每件都要办理一次手续，货物越多，运输本身也越费时间。合并包裹主要节省的是重复办理手续的成本。

用教学数值计算：α=5 微秒，B=10 GB/s，采用十进制单位。1,000 条各 1,024 字节的消息，总载荷为 1,024,000 字节，单算传数据需要 102.4 微秒。

| 逐条串行发送方式 | 启动成本 | 传数据时间 | 总计 |
| --- | --- | --- | --- |
| 1,000 条小消息 | 1,000×5 = 5,000 微秒 | 102.4 微秒 | 5,102.4 微秒 |
| 合成一条大消息 | 5 微秒 | 102.4 微秒 | 107.4 微秒 |

总字节没变，重复启动的次数减少了。这就是批量传输的价值。表格假设消息必须串行、没有排队，也没计入打包和等数据凑齐的时间；如果消息能并发，或者凑一批需要等很久，实际收益会改变。

### 4.2 延迟与带宽，分别回答什么问题？

**延迟**回答“一次请求要等多久”；**带宽**回答“持续工作时，一秒能运多少数据”。两者相关，但不是同一个指标。

可以想成输水管：水从入口走到出口需要时间，但只要管内持续有水，出口就可能一直有稳定流量。程序若有很多相互独立的请求，也可以让一批请求在路上时继续发下一批，从而隐藏部分等待。

要达到目标带宽 B，单次延迟为 L，平均在途数据量大约需要 B×L。例如 B=100 GB/s、L=100 ns，在途量约为 10,000 字节；若每次请求 64 字节，约需 157 个独立请求，才能覆盖这个量级。

这个计算说明为什么足够的请求并发很重要，不代表某款 CPU 一定能提供这些请求槽位。若每次必须等上一次结果才能知道下次地址，即便硬件带宽很高，也可能无法持续喂满通道。

### 4.3 边传边算：先做不依赖新边界的部分

回到网格。分区中间的点只读自己拥有的数据，不需要等待新 Halo；贴近分区边缘的点才需要它。因此可以：

```text
发起边界交换
      ↓
计算内部点             数据同时在传输
      ↓
确认交换完成
      ↓
计算边界点
```

设内部计算时间为 Tc，通信为 Tm，最后必须单独做的边界计算为 Tb。不重叠时是 `Tc+Tm+Tb`；理想重叠后为：

$$
T_{\mathrm{stage}}\approx\max(T_c,T_m)+T_b
$$

例如内部计算 8 毫秒、通信 5 毫秒、边界计算 2 毫秒，串行为 15 毫秒，理想重叠为 10 毫秒。通信没有消失，只是其中 5 毫秒被内部计算覆盖了。

必须仍遵守缓冲区规则：如果发送直接引用拥有区域的整行，发送完成前就不能更新该行。可以先算内部、等发送结束再算边缘，也可以另建打包缓冲区。本章模型先复制并完成交换，再更新，没有实测异步重叠。

## 5. 先分清“必须搬”与“实现额外搬”

看到程序搬了很多数据，下一步要判断这些搬运从哪里来。

第一类由当前分工造成。比如网格切成上下两半后，两边就必须交换交界处的数据。这叫**内在通信（Inherent Communication）**：在给定算法和分工下，为满足数据依赖而需要交换。换一种分工，需求也可能改变。

第二类是实现过程中多出来的搬运。比如只用一个 4 字节的数，却加载一整条缓存行；或者一个数本来要再用，却被挤出缓存，只能重新读。这叫**实现引入的额外通信（Artifactual Communication）**。

这两个词帮助我们寻找不同的优化方向：前者可以考虑改变任务分区、调整数据所有权；后者可以考虑遍历顺序、分块或减少临时数组。

还要说清楚统计的是哪条路径。同一份数据可以先经网络到达机器，再从主存进入缓存。减少网络字节，不一定同时减少主存字节。后面讨论“计算了多少、搬了多少”时，总要先选定观察的存储层级。

## 6. 用区域形状减少跨 Worker 通信

### 6.1 同样多的格子，可以有很不一样的边界

让每个 Worker 分到相同数量的网格点，有很多种方法：按连续几行分、隔几行轮流分，或者分成二维小方块。

```text
连续条带：       交错行：         二维方块：
AAAAAAAA        AAAAAAAA         AAAABBBB
AAAAAAAA        BBBBBBBB         AAAABBBB
BBBBBBBB        CCCCCCCC         AAAABBBB
BBBBBBBB        DDDDDDDD         AAAABBBB
CCCCCCCC        AAAAAAAA         CCCCDDDD
CCCCCCCC        BBBBBBBB         CCCCDDDD
DDDDDDDD        CCCCCCCC         CCCCDDDD
DDDDDDDD        DDDDDDDD         CCCCDDDD
```

图中每个字母代表一个 Worker，三种方式都把同一张 8×8 网格均分给四个人，每人负责 16 个点。直觉上，点与点之间只需要近邻数据，属于同一人的点越集中，需要跨所有者传递的边界就越少。交错行让许多相邻行归不同人，容易增加通信。

### 6.2 先比较一个分区：工作看面积，通信看边长

设总网格 N×N，P 个 Worker 均分，每人约有 N²/P 个点。先忽略整张网格的外边缘，只考虑具有完整邻居的内部块，并且只统计一次交换收到的边界值。

| 分工方式 | 每人的区域 | 每人收到的边界值数量 |
| --- | --- | --- |
| 连续行条带 | 宽 N，高 N/P | 上下一行，共约 2N |
| 循环交错行，P>1 | N/P 行散在各处 | 每行通常都需上下邻行，共约 2N²/P |
| 二维方块，P 为平方数 | 边长 N/√P | 四条边，共约 4N/√P |

这里每个人处理的点数相同，通信量却不同。对于连续条带，“点数/收到的值数”为 N/(2P)；二维方块为 N/(4√P)。P 越大，条带的这个比值下降得更快，通信相对计算会更突出。

注意这仍是几何模型：处理点数不是 FLOP，接收元素数也不是字节，暂时不要把它当作后面的算术强度。

### 6.3 再算整张网格：保留外边界后的精确例子

取 N=1024、P=16，比较 16 条横向条带与 4×4 个方块。一次交换中，每条内部切分线两边互相发送一份数据，不发送四角。

16 条带之间有 15 条切分线，每条长 1024，所以总共发送：

$$
Q_{\mathrm{strip}}=2\times1024\times15=30720\ \text{项}
$$

4×4 方块有 3 条横向、3 条纵向切分线，总共发送：

$$
Q_{\mathrm{tile}}=2\times1024\times(3+3)=12288\ \text{项}
$$

因此载荷比是 30720/12288=2.5。如果每项是 4 字节的 float32，分别为 122,880 和 49,152 字节。这里每个方向各计一次；发送量已包含整条链路载荷，不要再把接收量加上去算第二遍。

推广到 R 行、C 列的矩形分区，RC=P，同样的推导得到：

$$
Q_{\mathrm{values}}=2N(R-1)+2N(C-1)
$$

它与前面“一个内部 Worker”的估算不同：整张网格最外侧没有邻居，不需要向外发送，因此不能把两种口径的比率混为一谈。第 3 节实际 Halo 程序还发送了两端边界列，要按程序自身的 N+2 项计量。

### 6.4 方块为什么有利，又为什么不保证最快？

在面积相同的矩形中，接近正方形的周长最短。固定面积 A=hw，由 `(h−w)²≥0` 可得 `h+w≥2√A`，等号在 h=w 时成立。每个点只看近邻时，边界短就意味着需要交换的数据少。

但时间不只取决于字节数。方块通常有四个邻居，可能比条带需要更多消息；行主序数组中，列边界也可能需要额外打包。再加上第 4 节的启动成本，少传字节的方案未必恰好最快。

**作者理解：** 分区是在同时做两笔账：一笔是“每人算多少”，另一笔是“每人为了计算要借多少数据”。负载均衡与局部性需要一起考虑。

## 7. 有限缓存：同一个数为什么读了又读？

### 7.1 把数据放近，还不够；要在它离开之前再用

前面讨论的是 Worker 之间的数据。现在把视角缩到一颗 CPU：主存中的数据被搬进缓存后，如果很快再次用到，就不用再去主存取一次。

这里有两种常见的局部性：

- **空间局部性：** 访问相邻地址。既然一次取来一整条缓存行，就尽量用到这行里的其他数。
- **时间局部性：** 短时间内再次使用同一个数据，让它留在缓存时多发挥作用。

对行主序数组，沿一行连续访问通常有较好的空间局部性。但是一行如果非常宽，扫描到最右边再回来处理下一行时，左边原先加载的数据可能已经被挤走。地址连续并不自动保证重复使用时还能命中。

### 7.2 一个只装得下两行的“工作台”

先看独立于具体 CPU 的小模型。缓存只能保存两个缓存行编号，满了就淘汰最久没使用的那一行，这种规则叫 **LRU（最近最少使用淘汰）**。

访问顺序为 `0,1,2,0,1,2`：

| 这次访问 | 访问后缓存中的行，左边较旧 | 是否未命中？ |
| --- | --- | --- |
| 0 | 0 | 是 |
| 1 | 0,1 | 是 |
| 2 | 1,2 | 是，0 被挤走 |
| 0 | 2,0 | 是，1 被挤走 |
| 1 | 0,1 | 是，2 被挤走 |
| 2 | 1,2 | 是，0 被挤走 |

六次全都未命中。如果问题允许把访问改成 `0,0,1,1,2,2`，每个编号第一次要加载，第二次马上命中，只剩三次未命中。

访问次数和不同数据数量都没变，差别在于“第二次使用之前隔了多少其他数据”。这段间隔通常与**复用距离**有关。优化局部性的一个常见思路，就是缩短这段距离。

这个模型使用精确 LRU，真实 CPU 不一定按同样规则替换缓存。我们借它理解因果关系，不用它代替硬件性能测量。

### 7.3 分块：把一次做的范围缩小

网格更新会反复使用相邻行的数据。与其每次扫完整个宽行，可以先处理一个较窄的列条带，沿它向下算，再移到下一个条带。这样的工作重排称为**分块（Blocking/Tiling）**。

```text
整行扫描：                 窄条带扫描：
先扫第 1 行 → → → →       先做左边小段，沿多行复用
再扫第 2 行 → → → →       [AAAA][BBBB]...
再扫第 3 行 → → → →       [AAAA][BBBB]...
                           [AAAA][BBBB]...
```

分块不是减少需要更新的点，而是让相邻更新需要的数据更有机会同时留在缓存里。一个简化估计是：如果要保留三段输入行，每段宽 b+2，每个元素 s 字节，输入窗口大约占 `3(b+2)s` 字节。其中额外的两列是左右邻居。

实际还要给输出和其他数据留空间，也会受缓存行对齐和冲突影响。因此这只是选择块大小的起点，不能据此精确预测每次未命中。

后面的模型固定 N=30，含边界行宽 32；每缓存行存 4 项，缓存能装 6 行，只统计输入读取。结果是：

| 遍历方式 | 输入缓存未命中次数 |
| --- | --- |
| 整行扫描 | 720 |
| 宽度 b=4 的条带 | 480 |
| 宽度 b=1 的条带 | 1380 |

为什么 b=1 反而更差？在这个模型中，条带过窄会让相邻条带再次读取重叠的邻居数据，之前加载的整条缓存行也未必得到充分利用。**分块要适合缓存和访问模式，并不是越小越好。**

这些数字来自明确配置的教学模型，不是本机真实缓存计数器，也不是所有网格尺寸的普遍规律。

### 7.4 改顺序之前，先确认不会改答案

有两种网格更新方式需要区分。

**双缓冲 Jacobi：** 一轮中始终从旧数组读，向另一个新数组写。每个输出都只依赖旧值，所以本轮输出点的计算顺序可以调整。

**原地更新：** 直接覆盖原数组。后面的点可能读取前面刚更新的值，改变次序就可能改变本轮结果。红黑方法允许调整同一颜色内部的顺序，但要保留红黑阶段之间的依赖。

因此，不能在某个块里连续做好几轮，再去处理别的块，却声称与每轮整体同步相同。数据版本已经变了。

本章 C++ 分块实验使用双缓冲 Jacobi，Python Halo 实验使用红黑更新；各自都与对应算法的参考解比较。它们用来说明不同问题，不能拿两者的时间直接比较分块收益。

## 8. 循环融合：保留计算，减少中间数组

### 8.1 为什么一条表达式会经过三遍数组？

对每个下标 i，我们希望计算：

$$
E_i=D_i+(A_i+B_i)\times C_i
$$

一种实现把它拆成三个完整数组操作：先算 `tmp1=A+B`，再算 `tmp2=tmp1×C`，最后算 `E=tmp2+D`。这很直观，但中间结果先写出去，下一步又要读回来。

另一种实现是在一个循环里完成同一个下标的整条表达式，再处理下一个下标。这叫**循环融合（Loop Fusion）**。

```text
三遍扫描：A,B → tmp1；tmp1,C → tmp2；tmp2,D → E

一遍融合：读 A[i],B[i],C[i],D[i]
                 ↓
          连续做加、乘、加
                 ↓
             写 E[i]
```

**作者理解：** 分块让“下次再用”发生得更早；融合让“下一个步骤”紧跟着当前步骤。两者都在缩短数据从产生到消费的距离。

### 8.2 逐项数清楚，到底省了什么

这里假设数组互不重叠，每项是 4 字节的 float32，暂时只按源程序的标量读写统计流量。

| 步骤 | 读取 | 写入 | 每元素读写次数 |
| --- | --- | --- | --- |
| tmp1=A+B | A、B | tmp1 | 3 |
| tmp2=tmp1×C | tmp1、C | tmp2 | 3 |
| E=tmp2+D | tmp2、D | E | 3 |
| 融合版本 | A、B、C、D | E | 5 |

三遍共 9 次读写，即 36 字节/元素；融合后为 20 字节/元素。两种版本都做一次乘法、两次加法，共 3 次浮点运算，计算量没有减少。

**算术强度（Arithmetic Intensity）**就是计算量除以数据流量。用 FLOP 表示浮点运算次数，单位为 FLOP/字节：

$$
I_{\mathrm{separate}}=\frac{3}{36}=\frac{1}{12},\qquad I_{\mathrm{fused}}=\frac{3}{20}=0.15
$$

它回答“每搬一字节，能完成多少计算”。融合让同样的计算对应更少的读写，所以强度提高。

课件中的 1/3 和 3/5 是每次标量访存对应的操作数，还没有除以 float32 的 4 字节；不能直接把那两个数标成 FLOP/字节。

### 8.3 少搬 16 字节，能快多少？

如果程序完全受这条数据通路的带宽限制，两个版本达到相同有效带宽，而且没有其他额外成本，那么时间与字节数成正比，预测加速比为：

$$
\frac{T_{\mathrm{separate}}}{T_{\mathrm{fused}}}\approx\frac{36}{20}=1.8
$$

这是有条件的流量预测。真实情况下，中间数组可能本就留在缓存；写分配和写回也可能增加主存流量，编译器还可能进一步优化。因此，“源码数出的字节数”不等于内存控制器实际搬过的字节数。

对 100 万个元素，这个逻辑模型给出 36 MB 与 20 MB。它有助于提出“融合减少了流量”的解释，但是否更快、快多少，还要测完成时间。

融合也可能有代价：活跃的临时值变多，增加寄存器压力；循环变复杂，可能影响向量化。只有确认计算顺序、数组重叠和其他消费者允许，才能删除中间数组。

浮点运算还涉及舍入。本章实验使用可精确表示的小数值，并加 `-ffp-contract=off` 保持示例运算步骤，做逐元素比较。一般程序应根据数值误差要求检查结果，而不是照搬“所有输出必须逐位相等”。

## 9. Roofline：把 FLOPs 与字节合成性能上界

### 9.1 先用一个简单任务理解两个限制

假设一个任务要做 100 次浮点运算，还要从选定的存储层级搬 100 字节。机器每秒最多完成 1,000 次这样的运算，通路每秒最多搬 100 字节。

单看计算，至少要 `100/1000=0.1 秒`；单看搬数据，至少要 `100/100=1 秒`。就算计算和搬运能完美重叠，整个任务也不可能短于 1 秒。算力再强，数据还没到就不能完成任务。

Roofline 就是把这两个限制放进同一个模型：**计算能力给出一条上限，数据供给能力给出另一条上限，性能不能超过其中更低的一条。**

### 9.2 把刚才的算例写成公式

对同一个任务，定义：

| 符号 | 含义 | 单位 |
| --- | --- | --- |
| F | 总浮点运算量 | FLOP |
| Q | 跨越所选存储层级的数据量 | 字节 |
| I=F/Q | 算术强度 | FLOP/字节 |
| π | 与该精度和运算类型匹配的计算上限 | FLOP/秒 |
| β | 对应通路的可持续带宽 | 字节/秒 |
| P=F/T | 实际完成计算的平均吞吐 | FLOP/秒 |

这里的 P 表示吞吐，不是前面分区中的 Worker 数；本节用同一个传统符号，但含义由表格重新定义。

至少需要 F/π 秒计算、Q/β 秒搬数据，因此：

$$
T\ge\max\left(\frac{F}{\pi},\frac{Q}{\beta}\right)
$$

再用 F 除以时间，就得到：

$$
P\le\min\left(\pi,\beta\frac{F}{Q}\right)=\min(\pi,\beta I)
$$

检查单位也能帮助理解：`字节/秒 × FLOP/字节 = FLOP/秒`。βI 表示“按照当前每字节的计算量，数据通路最多能供给多少浮点运算”。

模型给的是上界。程序还可能因为串行依赖、负载不均、分支、延迟无法隐藏或同步等待而低于它。

### 9.3 为什么画出来像一个屋顶？

取一台教学机器：计算上限 π=1000 GFLOP/s，带宽 β=100 GB/s，均为十进制单位。这不是本机硬件规格。

当 I=1 时，带宽最多支持 100 GFLOP/s；I=4 时支持 400；I=10 时正好达到计算上限 1000。再提高 I，带宽侧虽然还能供给更多计算，但机器的算术能力已经限制在 1000。

```text
吞吐上界 P（GFLOP/s）
1000 |                 /──────────── 计算上限
     |               /
 400 |       /                       左侧：数据供给受限
     |     /                         右侧：计算能力受限
 100 | /
   0 +----------------------------------------------
       1    4         10         20    I（FLOP/字节）
              形状示意，数值以下表为准
```

| I（FLOP/字节） | 带宽能支持的 βI（GFLOP/s） | 最终吞吐上界 |
| --- | --- | --- |
| 0.25 | 25 | 25 |
| 1 | 100 | 100 |
| 4 | 400 | 400 |
| 10 | 1000 | 1000 |
| 20 | 2000 | 1000 |

两条上限相交时，`βI=π`，所以转折点是：

$$
I^*=\frac{\pi}{\beta}=10\ \text{FLOP/字节}
$$

若只把算力提高四倍，带宽不变，计算上限变成 4000，转折点也移到 40。I=4 的程序仍受同样的供给上限限制，不能仅靠新增算术单元突破 400 GFLOP/s。

分块、融合往往通过减少 Q 提高 I，在带宽受限区间可能提高性能。但这要求它们没有引入更大的其他成本，最终仍要看实际运行时间。

### 9.4 怎样把图用对？

先确定分母的字节来自哪里。DRAM Roofline 应使用穿过 DRAM 接口的流量和对应带宽；L2 Roofline 则配对 L2 的流量与带宽。不能把缓存里反复读取的逻辑字节都算成 DRAM 字节。

计算量和峰值也要统一口径。例如乘加 FMA 通常算作 2 FLOP；单精度与双精度峰值可能不同，不能混用；单核心的工作量和带宽也不应随意搭配整机峰值。

如果强度为 20，测得 200 GFLOP/s，而模型上限是 1000，这说明还有差距，但图本身不能替你定位原因。可能是实际流量估少了，也可能是请求并发不足、串行依赖或同步等待。Roofline 提供检查方向，不是自动诊断报告。

补充一个读图细节：上面的示意用线性坐标，斜线斜率是 β；论文和工具常用双对数坐标，此时带宽段的几何斜率为 1，β 改变的是垂直位置。不要直接把双对数图上的角度读成带宽大小。

### 9.5 FLOP/s 更高，不一定更早做完

性能计数还要服从任务目标。假设两种算法能达到相同的正确性要求：

| 算法 | 总计算量 F | 吞吐 P | 时间 T=F/P |
| --- | --- | --- | --- |
| 旧算法 | 100 GFLOP | 100 GFLOP/s | 1 秒 |
| 新算法 | 10 GFLOP | 50 GFLOP/s | 0.2 秒 |

新算法报告的 FLOP/s 更低，却快了五倍，因为需要做的总工作少了。给程序添加无用算术，可能让算术强度和 FLOP/s 看起来更好，但不会因此把任务更早做完。

**作者理解：** Roofline 最有用的地方，是帮我们判断“应该减少搬运，还是检查计算效率”；最终评价优化，仍要回到相同任务、相同结果要求下的完成时间。

## 10. Contention：总量相同，集中到达也会变慢

### 10.1 同时来四个人，不等于能同时服务四个人

假设走到办公室要 5 分钟，服务者回答一个问题也要 5 分钟。四个人同时出发，在第 5 分钟一起到达。服务者只能依次处理，所以他们分别在第 10、15、20、25 分钟完成，平均从出发到结束为 17.5 分钟。

如果按预约错峰出发，每人走到时正好轮到自己，各自只花 10 分钟。但从第一人出发到最后一人完成，仍可持续 25 分钟：服务者每 5 分钟处理一个人的能力没有改变。

这个例子区分了**服务时间**与**排队时间**。程序中，内存控制器、网络端口和共享锁也可能像这位服务者一样，面对集中到达的请求。总字节相同，到达时机和资源分布不同，等待也会不同。

### 10.2 先在本地做，再少量汇总

例如要统计一个数组的总和，让每个元素都更新同一个共享计数器，会形成热点。可以让每个 Worker 先计算自己的局部和，最后只汇总一次。共享更新的数量便从“每个元素一次”降到“每个 Worker 一次”。

如果所有局部和仍同时挤向一个根节点，可以分层合并：先两两相加，再逐层向上。这就是树形归约的直觉。它能分散压力，但也增加层数和中间步骤；规模小、没有明显竞争时，未必比直接汇总更快。

分片队列、复制只读数据也在做类似的取舍：减少大家访问同一个位置的次数，换来更多存储或维护开销。若数据经常更新，副本还要同步，不能只看读请求变快。

### 10.3 写不同变量，也可能争同一条缓存行

这是作者补充的常见例子：两个线程分别更新不同计数器，如果它们恰好位于同一缓存行，硬件仍可能为写入权限反复交接整行。它叫**伪共享（False Sharing）**。

从程序变量看，双方没有更新同一个计数器；从硬件传输粒度看，它们却在争同一行。调整布局可能有帮助，是否值得则应在目标机器测量。

竞争的解决方向通常是减少共享访问、分散热点或平滑请求。随机等待有时能缓解短时拥挤，但也会增加延迟，不是所有场景通用的修复方法。

## 11. 从模型走到测量：怎样知道还该优化哪里？

### 11.1 先写下预期，再看测量是否支持它

以融合为例，我们的预期是：算术仍为每元素 3 FLOP，逻辑读写从 36 降到 20 字节，因此可能减少数据流量与临时空间。接下来才去测时间，看这个解释是否与结果一致。

比较前先固定输入、输出和正确性要求，保留简单可用的基线。记录硬件、编译选项、线程数和计时范围；预热并重复运行，用中位数或分布描述结果，避免只挑最快一次。

由时间 t 可以计算 `3N/t` 的吞吐，也可以计算逻辑字节数除以 t。但后者应叫**逻辑带宽**。若要说“DRAM 实际搬了多少”，还需要相应硬件计数器或可靠的测量方法。

CPU 使用率显示 100%，也不能说明算术单元已满负荷工作。等待内存的线程同样可能被操作系统记为忙。

### 11.2 诊断性改动，可以帮助缩小范围

课件补充材料建议做一些临时对照：减少计算、增加计算、把访问集中到少量数据，或移除某些同步，观察时间怎样变化。这些常被用作“高水位”诊断，目的在于提出和检验瓶颈假设。

例如，把所有访问临时改为 `A[0]` 后明显变快，说明数据访问值得调查。但编译器也可能把不变计算移出循环，甚至删除工作，所以还要检查实际执行了什么。

这样的诊断版本可能已经改变答案，不能直接发布为优化版。删锁后更快，也不表示最终代码可以不用锁；原本需要保护的访问可能已经发生数据竞争。

### 11.3 让一次实验只回答一个主要问题

先确认输出，再单独调整块大小或是否融合。若同时更换算法、精度、线程数和停止标准，就很难解释时间为什么变了。

对于迭代求解器尤其要小心：一轮更快，但可能要更多轮才能达到相同误差。因此公平比较应看“达到相同残差或误差需要多久”，而不只是每轮耗时。

一个实用顺序是：**确认结果 → 解释数据路径 → 估计成本 → 改一个因素 → 测量并检查解释**。模型与测量不一致时，优先检查假设，不必硬把结果套回预计的倍数。

## 12. 问题规模与机器规模要一起看（课件补充）

本节依据课件后半部分及作者推导补充。用户文字稿结束于 Roofline 提问，不能将本节写成该段口述已经详细覆盖的内容。

### 12.1 同一道题加人，与每人多接一份题，是两种扩展

**强扩展（Strong Scaling）：** 总问题固定，增加 Worker，观察同一任务是否更快。比如始终更新同一个 1024×1024 网格，从 4 人增到 16 人。

**弱扩展（Weak Scaling）：** Worker 增加时，总问题也增大，让每人的工作量大致不变。比如二维方块划分中，Worker 增加四倍，同时让 N 增加两倍，每人点数仍是原来的数量。

强扩展时，每人的面积约 N²/P，边界约 N/√P。随着 P 增大，面积下降得比边界更快，所以通信占比容易上升。直观地说：小块里要算的点已经很少，但仍得完成一轮边界交接。

弱扩展让 N 随 √P 增长，块的边长 N/√P 可以不变，所以近邻通信相对更容易保持。但全局归约、网络拓扑和任务不均衡仍可能恶化，并不保证整套程序等比例扩展。

### 12.2 为什么有时会看到超过 Worker 数的加速比？

如果单核心处理全部数据时，工作集装不进缓存，会反复访问主存；分到多个核心后，每人只处理较小一部分，反而能够留在各自缓存中。这样除了增加计算资源，还减少了每份工作的远处访存成本，加速比就可能超过 Worker 数。

这叫超线性加速的一种来源。它不意味着单个核心凭空变强，而是总缓存容量和数据行为发生了变化。若基线还涉及磁盘换页，差异可能更夸张；报告时应解释清楚容量、基线与算法。

### 12.3 小问题未必喂得饱大机器

把很小的网格分给很多人，每人只剩少量点，启动、同步和边界交换可能比计算本身还贵。机器更多，未必更快。

课件第 66 页的一个算例还需要修正：258×258 个点分给 32 人，直接相除是 2080.125 项/人，并非页中约 310；若 258 含边界、内部为 256×256，则为 2048。这里保留“小问题利用不了大机器”的概念，不猜测错误数字的来源。

作为对照，1024×1024 的内部网格分给 32 人，每人约 32768 个点。判断是否足够，仍要结合每点计算成本和通信开销，而不能只看格子数量。

```python
"""Deterministic teaching models, not MPI or a hardware performance simulator."""
from collections import OrderedDict
from math import isclose


def rendezvous(p, parity):
    programs = [[] for _ in range(p)]
    def pair(a, b, first):
        programs[a].extend([(first, b), ('R' if first == 'S' else 'S', b)])
    for rank in range(p):
        if not parity:
            peers = [q for q in (rank-1, rank+1) if 0 <= q < p]
            programs[rank] = [('S', q) for q in peers] + [('R', q) for q in peers]
        elif rank % 2 == 0:
            for q in (rank+1, rank-1):
                if 0 <= q < p: pair(rank, q, 'S')
        else:
            for q in (rank-1, rank+1):
                if 0 <= q < p: pair(rank, q, 'R')
    pos = [0]*p
    while True:
        if all(pos[r] == len(programs[r]) for r in range(p)): return True
        progress = False
        for r in range(p):
            if pos[r] == len(programs[r]): continue
            op, q = programs[r][pos[r]]
            if pos[q] == len(programs[q]): continue
            other, peer = programs[q][pos[q]]
            if peer == r and op != other:
                pos[r] += 1
                pos[q] += 1
                progress = True
        if not progress: return False


def grid(n):
    a = [[0.0]*(n+2) for _ in range(n+2)]
    a[0] = [1.0]*(n+2)
    return a


def update(a, i, j):
    return 0.2*(a[i][j]+a[i-1][j]+a[i+1][j]+a[i][j-1]+a[i][j+1])


def halo_case(n, p, sweeps):
    # p <= n: each rank owns at least one row. lo is a zero-based interior offset.
    reference = grid(n)
    ranks = []
    for r in range(p):
        lo, hi = r*n//p, (r+1)*n//p
        local = [row[:] for row in reference[lo:hi+2]]
        ranks.append((lo, hi-lo, local))
    total_values = 0
    for _ in range(sweeps):
        for color in (0, 1):
            # Snapshot every sender before delivering: this models a completed exchange.
            outgoing = [(a[1][:], a[h][:]) for lo, h, a in ranks]
            for r, (lo, h, a) in enumerate(ranks):
                if r > 0:
                    a[0] = outgoing[r-1][1][:]
                    total_values += n+2
                if r+1 < p:
                    a[h+1] = outgoing[r+1][0][:]
                    total_values += n+2
            for lo, h, a in ranks:
                for i in range(1, h+1):
                    for j in range(1, n+1):
                        if (lo+i+j) % 2 == color: a[i][j] = update(a, i, j)
            for i in range(1, n+1):
                for j in range(1, n+1):
                    if (i+j) % 2 == color: reference[i][j] = update(reference, i, j)
            for lo, h, a in ranks:
                assert a[1:h+1] == reference[lo+1:lo+h+1]
                assert all(a[i][0] == a[i][-1] == 0 for i in range(1, h+1))
            assert ranks[0][2][0] == [1.0]*(n+2)
            assert ranks[-1][2][-1] == [0.0]*(n+2)
    assert total_values == 4*(p-1)*(n+2)*sweeps
    return total_values


def remote_values(n, rows, cols):
    # Directed halo payload across all internal rectangular partition interfaces.
    return 2*n*(rows-1) + 2*n*(cols-1)


def cache_misses(n, width):
    # Only input reads of a double-buffered stencil; output has a separate cache.
    # Fully associative LRU, 6 lines, 4 scalar elements/line, stride n+2.
    cache = OrderedDict()
    misses = 0
    for jj in range(1, n+1, width):
        for i in range(1, n+1):
            for j in range(jj, min(jj+width, n+1)):
                for x, y in [(i,j),(i-1,j),(i+1,j),(i,j-1),(i,j+1)]:
                    line = (x*(n+2)+y)//4
                    if line not in cache:
                        misses += 1
                        if len(cache) == 6: cache.popitem(last=False)
                    cache[line] = None
                    cache.move_to_end(line)
    return misses


def main():
    for p in range(2, 10):
        assert not rendezvous(p, False)
        assert rendezvous(p, True)
    print('rendezvous: 8 send-first deadlocks detected; 8 parity schedules complete')
    cases = 0
    for n in [1, 2, 3, 5, 8, 11]:
        for p in range(1, min(n, 4)+1):
            for sweeps in [1, 2, 7]:
                halo_case(n, p, sweeps)
                cases += 1
    print(f'halo: cases={cases} every_color=pass boundaries=pass payload=pass')
    assert halo_case(8, 2, 1) == 40
    n, p = 1024, 16
    strip, tile = remote_values(n, p, 1), remote_values(n, 4, 4)
    assert (strip, tile) == (30720, 12288)
    print(f'partition N=1024 P=16: strip={strip} tile={tile} values/exchange')
    row, blocked = cache_misses(30, 30), cache_misses(30, 4)
    assert blocked < row
    print(f'LRU input-only N=30: row={row} strip_width4={blocked} misses')
    f, q1, q2 = 3, 36, 20
    assert isclose((f/q2)/(f/q1), 1.8)
    peak, bandwidth = 1000, 100  # GFLOP/s and GB/s; decimal prefixes cancel.
    assert peak/bandwidth == 10
    for intensity in [0.25, 1, 4, 10, 20]:
        print(f'roofline I={intensity:g}: {min(peak, bandwidth*intensity):g} GFLOP/s')
    assert 258*258/32 == 2080.125
    print('fusion: 36 -> 20 logical bytes/element; ideal bandwidth-only speedup=1.8')
    print('all_checks=pass')


if __name__ == '__main__':
    main()
```

## 14. C++17 实验：完整融合与空间分块

这一节把“融合不改变结果”和“空间分块不改变 Jacobi 每轮输出”放进真实 C++ 程序验证。可以先运行正确性检查，再尝试可选计时。

### 14.1 测试设计

融合部分比较三次扫描、单次融合与独立算术参考，覆盖空数组、短数组和非整齐长度。空间分块部分采用双缓冲 Jacobi，按完整行的参考实现与 Tile 实现比较每轮结果，同时检查边界和值域。

不需要线程、GPU 或 MPI。这里单线程同样能展示局部性优化；并行调度不会自动替你消除临时数组。

### 14.2 完整代码

保存为 `locality.cpp`：

```cpp
#include <algorithm>
#include <chrono>
#include <cmath>
#include <iomanip>
#include <iostream>
#include <stdexcept>
#include <string>
#include <vector>
using Vec = std::vector<float>;
using Clock = std::chrono::steady_clock;

void separate(const Vec& a, const Vec& b, const Vec& c, const Vec& d,
              Vec& t1, Vec& t2, Vec& out) {
    for (std::size_t i=0; i<a.size(); ++i) t1[i]=a[i]+b[i];
    for (std::size_t i=0; i<a.size(); ++i) t2[i]=t1[i]*c[i];
    for (std::size_t i=0; i<a.size(); ++i) out[i]=d[i]+t2[i];
}
void fused(const Vec& a, const Vec& b, const Vec& c, const Vec& d, Vec& out) {
    for (std::size_t i=0; i<a.size(); ++i) out[i]=d[i]+(a[i]+b[i])*c[i];
}
void inputs(Vec& a, Vec& b, Vec& c, Vec& d) {
    for (std::size_t i=0; i<a.size(); ++i) {
        a[i]=static_cast<int>(i%17)-8;
        b[i]=0.25f*static_cast<int>(i%7);
        c[i]=0.5f; d[i]=1.0f;
    }
}
struct Grid {
    int n, stride;
    Vec x;
    explicit Grid(int size):n(size),stride(size+2),x(stride*stride,0) {
        std::fill(x.begin(),x.begin()+stride,1);
    }
    float& at(int i,int j) { return x[i*stride+j]; }
    float at(int i,int j) const { return x[i*stride+j]; }
};
void reference_step(const Grid& in, Grid& out) {
    for (int i=1; i<=in.n; ++i)
        for (int j=1; j<=in.n; ++j)
            out.at(i,j)=0.2f*(in.at(i,j)+in.at(i-1,j)+in.at(i+1,j)
                                  +in.at(i,j-1)+in.at(i,j+1));
}
void stencil(const Grid& in, Grid& out, int tile) {
    for (int ii=1; ii<=in.n; ii+=tile)
        for (int jj=1; jj<=in.n; jj+=tile)
            for (int i=ii; i<std::min(ii+tile,in.n+1); ++i)
                for (int j=jj; j<std::min(jj+tile,in.n+1); ++j)
                    out.at(i,j)=0.2f*(in.at(i,j)+in.at(i-1,j)+in.at(i+1,j)
                                          +in.at(i,j-1)+in.at(i,j+1));
}
void check() {
    int fusion_cases=0, stencil_cases=0;
    for (int n : {0,1,2,3,7,16,31,33,257}) {
        Vec a(n),b(n),c(n),d(n),t1(n),t2(n),x(n),y(n);
        inputs(a,b,c,d);
        separate(a,b,c,d,t1,t2,x); fused(a,b,c,d,y);
        if (x!=y) throw std::runtime_error("fusion mismatch");
        for (int i=0; i<n; ++i) {
            double expected=double(d[i])+(double(a[i])+b[i])*c[i];
            if (x[i]!=expected) throw std::runtime_error("reference mismatch");
        }
        ++fusion_cases;
    }
    for (int n : {1,2,3,7,16,31})
        for (int tile : {1,2,3,8,64})
            for (int steps : {1,2,7}) {
                Grid a(n),b(n),x(n),y(n);
                for (int s=0; s<steps; ++s) {
                    reference_step(a,b); stencil(x,y,tile);
                    std::swap(a.x,b.x); std::swap(x.x,y.x);
                    if (a.x!=x.x) throw std::runtime_error("stencil mismatch");
                }
                for (int i=0; i<n+2; ++i)
                    for (int j=0; j<n+2; ++j) {
                        float v=x.at(i,j);
                        if (!std::isfinite(v)||v<0||v>1)
                            throw std::runtime_error("invalid grid value");
                        if ((i==0 && v!=1) || (i==n+1 && v!=0) ||
                            (i>0 && (j==0||j==n+1) && v!=0))
                            throw std::runtime_error("boundary changed");
                    }
                ++stencil_cases;
            }
    std::cout<<"fusion_cases="<<fusion_cases<<" stencil_cases="<<stencil_cases
             <<" boundaries=pass correct=yes\n";
}
double checksum(const Vec& x) {
    double sum=0;
    for (float v:x) sum+=v;
    return sum;
}
void bench(std::size_t n) {
    Vec a(n),b(n),c(n),d(n),t1(n),t2(n),x(n),y(n);
    inputs(a,b,c,d);
    separate(a,b,c,d,t1,t2,x); fused(a,b,c,d,y);
    if (x!=y) throw std::runtime_error("warmup mismatch");
    std::vector<double> times[2];
    double observed=0;
    for (int rep=0; rep<7; ++rep)
        for (int order=0; order<2; ++order) {
            int mode=(rep+order)%2;
            auto start=Clock::now();
            if (mode==0) separate(a,b,c,d,t1,t2,x);
            else fused(a,b,c,d,y);
            double seconds=std::chrono::duration<double>(Clock::now()-start).count();
            times[mode].push_back(seconds);
            // Observe every timed output outside the timed region.
            observed+=checksum(mode==0 ? x : y);
            if (x!=y) throw std::runtime_error("timed output mismatch");
        }
    std::cout<<std::fixed<<std::setprecision(3);
    for (int mode=0; mode<2; ++mode) {
        std::sort(times[mode].begin(),times[mode].end());
        double t=times[mode][3];
        std::cout<<(mode==0?"separate":"fused")<<" n="<<n
                 <<" median_ms="<<t*1000
                 <<" logical_GB_per_s="<<(mode==0?36.0:20.0)*n/t/1e9<<'\n';
    }
    std::cout<<"observed_checksum="<<observed<<" correct=yes\n";
}
int main(int argc,char** argv) {
    try {
        check();
        if (argc>1) {

                throw std::runtime_error("usage: locality [--bench [elements]]");

            bench(n);
        }
    } catch (const std::exception& e) {
        std::cerr<<e.what()<<'\n'; return 1;
    }
}
```

## 15. 练习与参考答案

前六题用于检查直觉，后面再做计算与工程判断。公式记不住时可以回到例子，先写出“总工作量、总字节数、等待关系”再算。

### 练习 1：共享数组为什么也会慢？

两个线程都能读取 `A[i]`，为什么还要关心数据在哪里？

**答：** 可以访问不等于数据就在附近。一个线程可能直接命中缓存，另一个可能需要经更远路径读取。即使访问同一个地址，缓存、内存节点与排队状态也可能不同。

### 练习 2：发送返回，是否表示对方已经用完数据？

`MPI_Send` 返回后，能否断定接收方已经处理完消息？

**答：** 不能。它保证发送缓冲区可以复用，消息也可能还在系统缓冲区。若要知道对方处理结束，需要另外约定应用级确认。

### 练习 3：Halo 保存的是什么？

Rank 0 的下幽灵行存着 Rank 1 的第一条拥有行。Rank 0 能否直接把这条幽灵行当成自己的点更新？

**答：** 不能。它只是邻居数据的副本，真正的数据由 Rank 1 更新。Rank 0 要在约定阶段接收新副本，确保读到正确版本。

### 练习 4：一轮为什么需要交换两次？

在红黑更新中，一开始交换边界，然后连续算完红色和黑色，哪里会出错？

**答：** 黑色边缘点需要邻居刚更新的红值，而幽灵行里仍是旧值。红阶段后需要再交换，或用其他能提供同版本数据的协议。

### 练习 5：异步发送时能先改一半数据吗？

发送缓冲区是一整行，发送还没完成，只修改其中的红点是否安全？

**答：** 不安全。仍在修改发送中的缓冲区。可以等发送完成后再改，或先把要发的数据复制到独立缓冲区。

### 练习 6：缓存顺序

缓存能装两行，按 LRU 淘汰。为什么 `0,1,2,0,1,2` 比 `0,0,1,1,2,2` 更容易未命中？

**答：** 前者再次使用某行之前，它已经被其他两行挤走，六次都未命中；后者第二次访问紧接第一次，共三次未命中。差别在重复使用的间隔，不在总访问次数。

### 练习 7：别忘了全局颜色

一个 Rank 前面已经分出 ℓ=2 行，它的本地行 i=1、列 j=2 是什么颜色？如果 ℓ=3 呢？

**答：** 按 `(ℓ+i+j)%2`，分别为 1（黑）和 0（红）。只看本地 `(i+j)%2` 会漏掉全局偏移。

### 练习 8：哪种分区传得少？

N=120、P=12，按 12×1 与 3×4 划分，一次交换的全局总发送元素数各是多少？只统计内部切分线，不计角点和额外边界列。

**答：** 12×1 有 11 条切分线，载荷为 `2×120×11=2640`。3×4 有 2 条横线、3 条纵线，载荷为 `2×120×(2+3)=1200`。比率是 2.2；这是载荷比，不是保证的速度比。

### 练习 9：小消息的启动成本

α=2 微秒，B=1 GB/s，100 条各 100 字节的消息逐条串行发送，与合成一条相比，各要多久？

**答：** 总载荷 10000 字节，传输时间为 10 微秒。小消息共启动 100 次，总计 `200+10=210` 微秒；合并后为 `2+10=12` 微秒。尚未计入组批等待和打包。

### 练习 10：融合后为什么强度提高？

每元素仍做 3 FLOP，改用每项 8 字节的 float64。三次扫描与融合版本的逻辑强度各是多少？

**答：** 三次扫描 9 次标量读写，共 72 字节，强度为 3/72=1/24 FLOP/字节；融合 5 次，共 40 字节，强度为 3/40。流量比仍为 1.8，但不保证实际时间比相同。

### 练习 11：一步步算 Roofline

计算上限为 2 TFLOP/s，带宽 200 GB/s，任务强度 I=2 FLOP/字节。转折点和吞吐上界各是多少？

**答：** 先统一单位，2 TFLOP/s=2000 GFLOP/s。转折点为 `2000/200=10 FLOP/字节`；带宽侧只能支持 `200×2=400 GFLOP/s`，低于计算上限，所以吞吐上界为 400。若只测到 50，还需查实际流量、请求并发、依赖和同步，不能说带宽已经用满。

### 练习 12：吞吐低一些，仍能更快？

旧算法做 80 GFLOP，吞吐 400 GFLOP/s；新算法做 20 GFLOP，吞吐 200 GFLOP/s。谁先做完？

**答：** 用计算量除以吞吐：旧算法 0.2 秒，新算法 0.1 秒。新算法快两倍，因为总工作量更少。

### 练习 13：块越大或越小都更好吗？

模型中 b=4 比 b=1 未命中少，能否宣布本机最优块宽为 4？

**答：** 不能。小块可能增加重复邻居读取，大块可能放不进缓存。模型还省略输出、预取等因素；应在目标程序上扫描多个块大小和输入尺寸，先验证结果，再比较时间。

### 练习 14：预约提高了哪一种体验？

服务者每 5 分钟处理一个人。错峰到达减少了等待，是否说明处理能力增加了？

**答：** 没有。减少的是队列里的等待，服务者仍每 5 分钟处理一个人。响应时间与服务吞吐需要分别看。

### 练习 15：弱扩展怎样保持每人工作不变？

二维网格按方块划分，Worker 数增加四倍，N 应怎样变化，才能让每人点数不变？

**答：** N 增加两倍，因为 `(2N)²/(4P)=N²/P`。块边长也不变，但全局归约和网络成本仍可能增长。

### 练习 16：通信重叠能省多少？

内部计算 Tc=3 毫秒，通信 Tm=8 毫秒，边界计算 Tb=1 毫秒。串行与理想重叠各要多久？

**答：** 串行为 12 毫秒；理想重叠为 `max(3,8)+1=9` 毫秒。只能隐藏 3 毫秒，通信仍是较长的一段；不能把两者中较短的时间从结果里算两次。

## 16. 与 AI Infrastructure 的联系（作者延伸）

在深度学习程序中，中间数组常变成中间 Tensor。算子融合让一个操作刚产生的数据尽快被下一个操作使用，可能减少写回大容量存储再读回的过程。但寄存器、片上容量和执行并发都有限，仍要权衡融合范围。

多设备计算也有开头那张网格的问题：工作分得均匀，设备之间却可能需要频繁交换激活或状态。有时稍不均匀、但能大量减少通信的分工，反而总时间更短，需要同时比较计算与数据路径。

批量通信可以摊薄启动成本，通信重叠可以覆盖等待，但前者可能引入等数据凑齐的时间，后者需要独立工作与正确同步。对于服务系统，还要分别看吞吐和用户等待时间。

这些是本章思路的延伸。CPU 主存、GPU 显存、主机与设备链路、跨节点网络的带宽与流量口径各不相同；分析完整训练或推理系统时，需要沿实际路径逐层建模。
